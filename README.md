# RLExploration

RLExploration is a hands-on reinforcement learning playground for experimenting with environments, algorithms, and intelligent agents. Each mini-project lives in its own directory, keeping its source code, configuration files, dependencies where needed, and generated models organized independently.

## Running a Mini-Project

Run commands from the repository root using Python's module execution syntax:

```bash
uv run python -m example.main
uv run python -m example.train
uv run python -m example.test
```

Replace `example` with the package name of the mini-project you want to run. For example, a mini-project located in `blackjack/` with an appropriate package structure can be run using:

```bash
uv run python -m blackjack.main
```

This approach uses the repository's Python environment managed by `uv` and allows modules to resolve their package-relative imports correctly. Run commands from the repository root unless a mini-project explicitly documents otherwise.

## Importing Mini-Project Modules

Modules within a mini-project should use relative imports when accessing other modules in the same package.

For example, inside `example/main.py`:

```python
from .config import load_config
from .game import GridGame
```

To import a module from another mini-project or from an external script, use its package-qualified name:

```python
from example.config import GridConfig, load_config
from example.game import GridGame
from example.env import GridNavigationEnv
```

The directory must be importable as a Python package, typically by including an `__init__.py` file. When importing one mini-project from another, ensure the repository root is on Python's import path and avoid relying on the current working directory to locate source modules.

## Configuration Paths

Configuration files should be resolved relative to the module that owns them, rather than the process's current working directory. This allows a mini-project to load its configuration consistently when launched from the repository root or imported by another module.

For example, `example/config.py` can locate its default configuration file using `pathlib`:

```python
from dataclasses import dataclass
from pathlib import Path
import json


@dataclass
class GridConfig:
    width: int
    height: int
    cell_size: int


CONFIG_PATH = Path(__file__).resolve().parent / "config.json"


def load_config(
    config_path: str | Path | None = None,
) -> GridConfig:
    path = (
        Path(config_path).expanduser().resolve()
        if config_path is not None
        else CONFIG_PATH
    )

    with path.open("r", encoding="utf-8") as file:
        data = json.load(file)

    return GridConfig(**data)
```

With this design, calling `load_config()` loads the default `config.json` located beside `config.py`. To use a different configuration file, pass its path explicitly:

```python
# Load the default configuration.
config = load_config()

# Load a custom configuration using a relative path.
config = load_config("configs/experiment.json")

# Load a configuration using an absolute path.
config = load_config("/path/to/custom_config.json")
```

An explicitly supplied relative path is resolved against the current working directory. Use an absolute path when the configuration must be located independently of where the command is launched.

Parse the configuration once and pass the resulting configuration object to the components that need it:

```python
config = load_config("example/config.json")

game = GridGame(config)
env = GridNavigationEnv(config)
```

The constructor arguments above are illustrative of the configuration pattern; use the actual constructors provided by the mini-project.

## Model and Artifact Paths

Store generated models and experiment artifacts inside the corresponding mini-project rather than in a shared repository-level directory.

For example, a training script can define a project-local model directory:

```python
from pathlib import Path

PROJECT_DIR = Path(__file__).resolve().parent
MODEL_DIR = PROJECT_DIR / "models"
MODEL_DIR.mkdir(parents=True, exist_ok=True)

model_path = MODEL_DIR / "ppo_grid_nav"
model.save(str(model_path))
```

The resulting model is stored under `example/models/`, keeping it separate from models generated by other mini-projects. Apply the same approach to logs, checkpoints, evaluation results, and other generated files.

When loading a model, resolve its path consistently:

```python
model_path = PROJECT_DIR / "models" / "ppo_grid_nav"
model = PPO.load(str(model_path), env=env)
```

Use the appropriate model class and filename for the algorithm and framework used by the mini-project.

## General Conventions

- **Isolation:** Keep each experiment's code, configuration, and generated artifacts within its own directory.
- **Package imports:** Use package-relative imports inside a mini-project and package-qualified imports when accessing it externally.
- **Module execution:** Prefer `uv run python -m package.module` from the repository root.
- **Path handling:** Use `Path(__file__).resolve().parent` for paths anchored to a module or mini-project, and accept explicit paths when customization is needed.
- **Configuration reuse:** Parse configuration files into structured objects where appropriate and pass those objects to components instead of repeatedly loading the same configuration.
- **Experiment independence:** Avoid hard-coded paths that assume a particular launch directory or depend on another mini-project's internal structure.
